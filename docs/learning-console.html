Architecture

One engine, two platforms, one set of tests

The whole design turns on one idea: separate what you test from how you tap it on each platform — and keep everything app-specific out of the code.

◆ you edit
automation.config.js  ·  .env
Your app's facts (ids, devices, TestRail) and your machine's secrets. Pure data — the config is committed, the .env is git-ignored and overrides it.
engine
core/
The machinery — driver, session, reporting, runner, matrix, TestRail, verdict. Written once; you never edit it.
◆ you edit
platforms/<ios|android>/pages/
Page objects: the selectors and steps for one platform. Same method names on both sides.
◆ you edit
specs/
One spec per section says what to test, in plain steps. Platform-agnostic — it calls page-object methods without knowing the OS.
The one idea to keep

A spec is the script; a page object is the stage directions for each actor (iOS / Android); core/ is the theatre that runs the show and reports what happened. Because a spec only calls pages.auth.signUp(), the same spec drives both platforms.

Life of a run

What happens when you click "Run pipeline"

One regression, from a button press to a red/green verdict. Each stage maps to a real file.

1

Trigger with a build URL

You upload an .apk/.ipa to BrowserStack (a bs:// URL) and start a pipeline, choosing TEST_SECTIONS. An empty URL skips that platform — it isn't a failure.

bitbucket-pipelines.yml
2

Fan out across devices

Per platform, the matrix runner launches one test process per device, in parallel — each an independent BrowserStack session, all grouped under one build name.

core/matrix.js
3

Open a session, run the sections

Each process opens an Appium session and Mocha runs the chosen sections. auth always runs first, so subsets start signed-in.

core/runner.js · core/section-registry.js
4

Drive the app, record everything

Page objects tap and type via our Appium client. Each test annotates the video with ▶ START / ✅ PASS / ❌ FAIL and a [mm:ss] mark; failures grab a screenshot and page source.

core/driver.js · core/helpers.js
5

Publish to TestRail

The matrix collects each device's summary, finds or creates the plan, and posts every C### case result. Once configured, a publish failure fails the run.

core/testrail.js
6

The verdict — the only red/green

Test steps always show green (they record their result to test-status/). The final step reads every summary and decides the pipeline's true pass/fail.

core/verdict.js
