OFFLINE LEARNING CONSOLE

One proven path from app build to regression verdict.

This repository is a reusable starting point for checks that operate an Android or iPhone/iPad app and confirm what appears on screen. The tests can be mapped, written, reviewed, and run entirely by hand, or Claude can guide the same work when project policy permits it.

Choose MANUAL-WORKFLOW.md when AI is prohibited, or AI-GUIDED-WORKFLOW.md when Claude is approved to map and write the tests. New Claude users only need to type “help me get started”. You work in your own downloaded copy of the template — the folder you unzipped — so there is no copy step; setup happens directly there. Both paths produce the same JavaScript suite.

How a CI run moves

APK / IPA bs:// upload WDIO per device JSON + JUnit TestRail Final report

A platform test step records its exit code instead of stopping the pipeline. That guarantees the last report can combine Android and iOS and become the single authoritative verdict.

1. Map before coding

  1. Find app IDs and launch entry points.
  2. Sketch navigation and state prerequisites.
  3. Record stable accessibility IDs.
  4. Match existing TestRail cases, or record the local-only route.

Write this into app-map/APP-MAP.md.

2. Keep sessions observable

wdio.conf.js creates the session. The official BrowserStack service receives the app URL and enables Test Observability. The driver only wraps WDIO commands; it never opens a second raw session.

3. Make failures useful

  • Every meaningful action has a named step().
  • A failed test records selector, error, video timestamp, PNG and XML.
  • Recovery restarts the app before the retry or next test.
  • The circuit breaker stops long cascades of meaningless failures.

4. Publish cases, not implementation details

it("C123 [1/2] Opens settings", ...)
it("C123 [2/2] Cancels deletion", ...)

The publisher merges these into case C123. Failure wins; otherwise a pass wins over a skip. Elapsed values are never below one second. Teams without TestRail use reviewed LOCAL-* labels for local runs; those labels cannot enter BrowserStack or CI.

5. Validate safely

find android ios ci onboarding -path '*/node_modules' -prune -o \
  -type f -name '*.js' -print0 |
  xargs -0 -n1 node --check

(cd android && npm run test:testrail)
(cd ios && npm run test:testrail)
node ci/report.self-test.js

These checks need no device, BrowserStack account, or live TestRail write.

6. Scale deliberately

The default matrices contain two devices per platform. Both platform steps in parallel can therefore open four sessions. Use BS_MATRIX_CONCURRENCY=1 when account capacity is lower.

The safest first milestone

  1. Confirm you are working in your downloaded copy of the template.
  2. Prepare the tools, one virtual or physical device, and one app build.
  3. Map and adapt one non-destructive section; do not run starter placeholders.
  4. Confirm that focused section passes on the local device.
  5. Stop there if hosted services are not approved or required.
  6. If approved, run one BrowserStack device with verified C### mappings.
  7. Confirm its video, status, and TestRail result before expanding.
